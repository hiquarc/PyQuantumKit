# Storage and Interpretation of Measurement Results
For a quantum variable, besides deciding the allocation of its qubits, if it is to be measured, the storage of the classical results (0 or 1) obtained from the measurement also needs to be considered. In most quantum development frameworks, besides qubits, developers often also need to allocate classical bits to collect the measurement results. Therefore, in order to compile a high-level-language-level quantum program into an executable quantum circuit and at the same time correctly identify the substring corresponding to each quantum variable from the result `'0'`/`'1'` strings, the allocation of the classical bits storing the measurement results also needs to be considered for the measurement operation.

## I. Allocation of the Classical Bits Storing the Measurement Results
In the main function of a quantum program, the measurement operation is completed by calling the `measure()` method on the `QProgramBuilder` object, where the parameters are filled in turn with the quantum variables to be measured.
```python
def qmain1(builder : QProgramBuilder):
    qarr1 = QubitArray(3, 'qarr1')
    qarr2 = QubitArray(4, 'qarr2')
    builder.declare_qvars(qarr1, qarr2)

    # measure qarr1 and qarr2 in order
    builder.measure(qarr1, qarr2)
    # can be equivalently replaced by builder.measure_all()
```
Just as calling the `declare_qvars()` function completes the allocation of qubits, calling the `measure()` function likewise also performs the allocation of the classical bits storing the measurement results. In the above example, PyQuantumKit allocates classical bits No. 0~2 for storing the measurement results of `qarr1` and classical bits No. 3~6 for storing the measurement results of `qarr2`.

Since the parameters and order of calling `declare_qvars()` and `measure()` are the same, the `measure_all()` method (with no parameters) can be used to replace `measure(qarr1, qarr2)`.

The quantum circuit generated by compiling the program `qmain1` will contain 7 qubits and 7 classical bits for storing the measurement results, and since the parameters and order of calling `declare_qvars()` and `measure()` are the same, the qubits and classical bits with the same indices correspond one-to-one.

### Different measurement orders
When calling `measure()`, the order of the passed-in parameters does not necessarily have to be the same as when calling `declare_qvars()`; in that case the allocation method of the classical bits storing the measurement results is different.

The following program
```python
def qmain2(builder : QProgramBuilder):
    qarr1 = QubitArray(3, 'qarr1')
    qarr2 = QubitArray(4, 'qarr2')
    builder.declare_qvars(qarr1, qarr2)

    # measure qarr2 first, then qarr1
    builder.measure(qarr2, qarr1)
```
has the order `qarr2, qarr1` when calling `measure()`; in this case PyQuantumKit allocates classical bits No. 0~3 for storing the measurement results of `qarr2` and classical bits No. 4~6 for storing the measurement results of `qarr1`.

However, the order when calling `declare_qvars()` in this example is `qarr1, qarr2`, so the allocation of qubits is: qubits No. 0~2 are allocated to `qarr1` and qubits No. 3~6 are allocated to `qarr2`. Here the case arises where the qubit indices of the same quantum variable are inconsistent with the indices of the classical bits storing the measurement results.

### Measuring only some of the quantum variables
When calling `measure()`, it is also allowed to measure only some of the quantum variables.

The following program
```python
def qmain3(builder : QProgramBuilder):
    qarr1 = QubitArray(3, 'qarr1')
    qarr2 = QubitArray(4, 'qarr2')
    builder.declare_qvars(qarr1, qarr2)

    # measure only qarr2
    builder.measure(qarr2)
```
declares two quantum variables, `qarr1` and `qarr2`, but measures only `qarr2`. Therefore PyQuantumKit allocates classical bits No. 0~3 for storing the measurement results of `qarr2`, and the quantum circuit generated by compiling the program `qmain3` will contain 7 qubits and 4 classical bits for storing the measurement results, and these 4 classical bits exactly store the measurement results of `qarr2`.


## II. Does the Measurement Result String Start from the Left or from the Right?
In most quantum development frameworks, the result of running a quantum circuit is a dictionary composed of entries of the form `measurement result '0'/'1' string : occurrence count`; for example, the running result of a quantum circuit that prepares and measures a Bell state usually has the following form:
```
{'00': 491, '11': 509}
```
That is, the occurrence counts of the measurement results `'00'` and `'11'` are 491 and 509 respectively.

There is a question here: which qubit's measurement result does the first `'0'` and the second `'0'` in `'00'` correspond to respectively? In fact, for this question, different quantum development frameworks have different conventions. The Bell state example cannot show the difference, so let's look at another example.

```python
def qmain4(builder : QProgramBuilder):
    qarr1 = QubitArray(3, 'qarr1')
    qarr2 = QubitArray(4, 'qarr2')
    builder.declare_qvars(qarr1, qarr2)

    qarr1.create_state_by_01pm_str('110')
    qarr2.create_state_by_01pm_str('0101')
    
    builder.measure_all()
```
We try to compile the program `qmain4` into a quantum circuit and run it on the three quantum development frameworks Qiskit, QPanda3 and Quafu, and we find that the same quantum circuit produces two kinds of running results.

The result of running on Qiskit and QPanda3 is:
```
{'1010011': 1000}
```
while the result of running on Quafu is:
```
{'1100101': 1000}
```
As can be seen, these two results are exactly in reverse order.

According to the semantics of the program `qmain4`, the quantum variable `qarr1` corresponds to qubits No. 0~2 and its measurement results are stored in classical bits No. 0~2; the quantum variable `qarr2` corresponds to qubits No. 3~6 and its measurement results are stored in classical bits No. 3~6. Therefore, if the indices of the result string are required to exactly match the indices of the classical bits, it should be `'1100101'`, that is, the convention adopted by the Quafu framework: the leftmost character of the string corresponds to the measurement result of the first qubit, called the **convention of starting from the left**. Qiskit and QPanda3 adopt the opposite **convention of starting from the right**, that is, the rightmost character of the result string corresponds to the measurement result of the first qubit.

The characteristic of the left-start convention is that the index of a qubit is the same as the index of its corresponding result character in the string, which is relatively friendly for programming processing. The characteristic of the right-start convention is that, if the measurement results need to be interpreted as an integer, then this way is exactly the binary representation that conforms to human reading habits (the low-order bits are on the rightmost side). Perhaps Qiskit and QPanda3 adopt the right-start convention mainly for the convenience of humans reading in binary form.

In the official documentation of these quantum development frameworks, the order of the measurement result characters is not emphasized, or even not mentioned at all. However, if cross-platform quantum program development is to be realized, the difference in the measurement result character order conventions of different quantum development frameworks needs to be noted.

## III. Interpretation of Measurement Results
After compiling the quantum program (by calling the `build()` method) using the `QProgramBuilder` class object, the allocation of the qubits of the quantum program and the classical bits storing the measurement results is complete, and then the relevant methods for interpreting the running results can be called to interpret the results.

### Interpretation of a single 0/1 string: the `interpret_output_str()` method
For a `'0'`/`'1'` string representing the output result of one measurement, you can call the `interpret_output_str()` method on a `QProgramBuilder` object whose circuit compilation has been completed. The method prototype is:
```python
def interpret_output_str(self, output_str : str, protocol : str = 'l') -> dict:
```

- `output_str` is the `'0'`/`'1'` string representing one measurement result. Please note that **the length of the input string must match the number of classical bits allocated by the quantum program in the `QProgramBuilder` for storing the measurement results**, and it cannot contain any characters other than `'0'`, `'1'`, otherwise a `ResultInterpretError` exception is thrown.

    - For example, the number of classical bits allocated in the above programs `qmain1`, `qmain2` and `qmain4` is all 7, so for the `QProgramBuilder` class that compiles these three programs, `'0011001'` and `'1101111'` are legal strings for calling the `interpret_output_str()` method, while `'110'`, `'1101'` and `'11+-abc'` are not legal strings.

    - The number of classical bits allocated in the program `qmain3` is 4, so `'1101'` is a legal string for calling it, while `'110'` and `'0011001'` are not legal strings.

    - You can call the `n_measure_cbits()` method of the `QProgramBuilder` object to obtain the number of classical bits allocated for storing the measurement results.

- The `protocol` parameter specifies the convention according to which the interpretation is performed. Two protocols are currently supported:
    - `'l'` or `'L'`: interpret according to the convention of starting from the left (the default method);
    - `'r'` or `'R'`: interpret according to the convention of starting from the right.
    - You can call the `framework_interpret_protocol()` static method of the `QProgramBuilder` class to obtain the interpretation convention of a specific framework:
        
    ```python
    print(framework_interpret_protocol('qiskit'))       # -> 'r'
    print(framework_interpret_protocol('pyqpanda3'))    # -> 'r'
    print(framework_interpret_protocol('pyquafu'))      # -> 'l'
    ```
        
- The return value is the interpreted dictionary, whose structure is:

    `{variable name 1: value 1, variable name 2: value 2, ...}`
    
    where *variable name* is the string passed in when declaring the quantum variable (for example `'qarr1'` and `'qarr2'` in the previous examples), and *value* is the interpretation result for that quantum variable. For quantum variables of composite types, the interpretation is further performed recursively on their elements or fields.

    - The measurement result of a `Qubit` type variable will be interpreted as a single character `'0'` or `'1'`;
    - The measurement result of a variable of `QubitArray` type will be interpreted as a `'0'`/`'1'` string;
    - The measurement result of a variable of array (QArray) type will be interpreted as a list composed of the interpretation results of its elements.
    - The measurement result of a variable of struct (QStruct) type will be interpreted as a dictionary with the variable name of each field as the key and the corresponding field's interpretation result as the value.
    - The measurement result of a variable of tuple (QTuple) type will be interpreted as a list composed of the interpretation results of its fields.
    - The measurement result of a variable of union (QUnion) type will be interpreted as a dictionary containing only one active field.

**Note: The `interpret_output_str()` method only interprets the result string according to the allocated qubits and classical bits, so its behavior is only related to the variable declaration part and the measurement operation part of the compiled program, and is unrelated to the function body.** For example, although the function body parts of the programs `qmain1` and `qmain4` are different, their variable declaration parts and measurement operation parts are exactly the same, so the behavior of calling the `interpret_output_str()` method on the `QProgramBuilder` objects that compile them is the same.

Below we use `qmain4` to illustrate the execution process of this method. We first use `QProgramBuilder` to compile `qmain4`, then call its `n_qvars_qubits()` method and `n_measure_cbits()` method respectively to obtain the number of qubits and the number of classical bits allocated for the program `qmain4`.
```python
qpb = QProgramBuilder()
qpb.build(qmain4)
print(qpb.n_qvars_qubits())     # -> 7
print(qpb.n_measure_cbits())    # -> 7
```

We call the `interpret_output_str()` method with `'1100101'` and the left-start convention and print the return value:
```python
print(qpb.interpret_output_str('1100101', 'l'))
```
The output result is:
```
{'qarr1': '110', 'qarr2': '0101'}
```
According to the semantics of the program `qmain4`, the measurement results of the variable `qarr1` are stored in classical bits No. 0~2; when the left-start convention is adopted, the substring `'110'` formed by indices 0~2 of the string `'1100101'` is the result corresponding to the variable `qarr1`. Similarly, the measurement results of the variable `qarr2` are stored in classical bits No. 3~6, so the substring `'0101'` formed by indices 3~6 of the string `'1100101'` is the result corresponding to the variable `qarr1`.

If we instead use the right-start convention to interpret the same string `'1100101'`
```python
print(qpb.interpret_output_str('1100101', 'r'))
```
The output result is:
```
{'qarr1': '101', 'qarr2': '0011'}
```
The string needs to be reversed first so that the indices of the characters can correspond to the same indices of each qubit. After reversing `'1100101'` we get `'1010011'`, so the variable `qarr1` corresponds to the substring `'101'` formed by indices 0~2, while the variable `qarr2` corresponds to the substring `'0011'` formed by indices 3~6.

### Interpretation of the result dictionary: the `interpret_result_dict()` method
The `interpret_output_str()` method only interprets a single `'0'`/`'1'` string, while the `interpret_result_dict()` method can interpret a dictionary composed of entries of the form `'0'/'1' string : occurrence count`. In most quantum development frameworks, the result of running a quantum circuit is exactly such a dictionary, so the measurement results returned by the framework can be interpreted directly. The prototype of this function is:
```python
def interpret_result_dict(self, output_dict : dict, protocol : str = 'l') -> list:
```

- `output_dict` is the measurement result dictionary.
- The `protocol` parameter specifies the convention according to which the interpretation is performed. Two protocols are currently supported:
    - `'l'` or `'L'`: interpret according to the convention of starting from the left (the default method);
    - `'r'` or `'R'`: interpret according to the convention of starting from the right.
- The return value is a list composed of tuples `(interpretation result, occurrence count)`.

The `interpret_result_dict()` method calls the `interpret_output_str()` method on each key of the passed-in parameter `output_dict` to interpret it, then combines it with the corresponding value (occurrence count) into a tuple of the form `(interpretation result, occurrence count)`, and the return value is a list composed of all such tuples.

In the raw measurement result dictionary, the keys are `'0'`/`'1'` strings; strings are hashable, so they can be used as dictionary keys, thereby forming a dictionary composed of entries of the form `'0'/'1' string : occurrence count`. However, the interpretation result itself is a dictionary, and dictionaries are not hashable and cannot be used as dictionary keys, so the return result of the `interpret_result_dict()` method is represented in list form, with each element of the list being a tuple of the form `(interpretation result, occurrence count)`.

**Note:** Similar to the `interpret_output_str()` method, **the behavior of the `interpret_output_str()` method is only related to the variable declaration part and the measurement operation part of the compiled program, and is unrelated to the function body.**
